# Android bank alert import (issue #146)

## Scope and evidence
The 2026-11-27 owner instruction to complete outstanding Android issues activates this formerly deferred work. This checkpoint uses explicit paste from a user-selected bank alert, not automatic inbox access. Piraeus [alerts documentation](https://www.piraeusbank.gr/el/knowledge-hub/piraeus-alerts-genikes-plhrofories) describes purchase and withdrawal SMS; it does not publish message body templates. The parser's checked-in examples are **synthetic**, not authenticated bank formats. Real sanitized purchase and withdrawal templates and physical acceptance are required before claiming production compatibility.

## Native path
Quick Entry → receipt/SMS import → paste selected Piraeus alert → local bounded parser → editable review → explicit debit confirmation → current canonical account selection → ordinary Save. Cancel, lock or owner change clears raw input and bank review. Unsupported, mixed/foreign-currency, ambiguous, malformed, credit, authorization/OTP, URL and rejected/reversed messages fail closed. The parser accepts one explicit EUR monetary amount, one valid date, one masked card suffix, one unambiguous purchase/withdrawal type with bank brand, optional time, explicitly labelled merchant/ATM and country. Values are exact integer cents. No raw text, mask, time or country is persisted or sent; only owner-reviewed ordinary finance fields enter Quick Entry. No notification is sent, no server writes happen until explicit Save.

Debit cards have no authoritative account linkage; never infer an account from a masked suffix. Filter to unique canonical Piraeus-linked bank/savings accounts using the same provider matcher as existing Web parity, require explicit selection and preserve it (or invalid/blank selection) across refresh. ATM withdrawals use the existing withdrawal event to an explicitly selected cash account, not category expenses. Safe existing category suggestions and duplicate advisory (including withdrawal amount/date) require confirmation when relevant. Review is not proof of bank authenticity or a guarantee that a user cannot knowingly enter the same transaction twice.

## SMS/notification policy
[Google Play SMS/Call Log policy](https://support.google.com/googleplay/android-developer/answer/10208820) lists SMS-based money management as a possible exception with review; it is not blanket approval. [Google Play sensitive permission policy](https://support.google.com/googleplay/android-developer/answer/18265346) also forbids using alternative APIs to circumvent SMS restrictions. No READ_SMS, RECEIVE_SMS or NotificationListenerService is introduced, and the existing exact APK permission gate remains. Automatic opt-in ingestion still requires real templates, source/authenticity and sensitive-data handling review, and a documented policy-compliant distribution decision. Only synthetic fixtures in Git; never paste real PAN, PIN/OTP, bank balances or credentials into issues.

## Validation
Parser JUnit, canonical account projection, and production Compose host regressions cover the new path. Local JDK compilation and standalone 22 synthetic parser cases passed; mandatory exact-head CI and actual Piraeus/S24 tests remain separate. No Web/backend/schema changes, release request, signing changes or live financial writes.
